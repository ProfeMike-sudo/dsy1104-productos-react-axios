Conectar React con una API: Axios y DTO

Backend: Express o Spring BootFrontend: React, Atomic Design y BootstrapModalidad: Demostración y práctica
0 Qué vas a lograr

Al terminar esta guía, una pantalla React le habrá pedido productos a una API y le habrá enviado uno nuevo desde un formulario, todo con Axios. Vas a levantar el ejemplo, leer cada pieza del código y seguir un producto desde que lo escribes hasta que queda guardado.

El ejemplo tiene dos partes que se ejecutan por separado. Del backend hay dos versiones con el mismo contrato, y puedes elegir la que tu equipo usará en el proyecto semestral:

  • Backend con Node.js y Express. Guarda los productos en un archivo JSON.
  • Backend con Spring Boot. Usa JPA y una base H2 que vive en un archivo.
  • Frontend con React, Axios y React Bootstrap. Guarda y lista productos, con Atomic Design y props.algo. Funciona igual con cualquiera de los dos backends.

1 Cómo se conectan las piezas

Axios es un cliente HTTP para JavaScript. En esta aplicación corre en el navegador: envía una solicitud al backend y espera una respuesta. El diagrama muestra el camino completo.

  1. La persona abre la página o envía el formulario.
  2. React llama a una función del service.
  3. Axios envía un GET o un POST a la API.
  4. El backend valida, consulta o guarda, y responde con JSON.
  5. React guarda la respuesta en su estado y dibuja la lista de nuevo.

Una llamada HTTP tarda y puede fallar, así que Axios devuelve una promesa. await espera el resultado dentro de una función async, y try/catch deja mostrar un error si algo sale mal.

Son aplicaciones independientes. React no importa el código del backend ni toca sus datos. Solo envía solicitudes HTTP a sus rutas, y el backend (Express o Spring Boot) decide qué acepta y cómo lo guarda.

3 El contrato de la API

Para consumir una API necesitas conocer su contrato: la dirección, las rutas, los métodos, los datos de entrada y las respuestas. Los repositorios ya lo traen. Aquí te toca ver cómo lo usa el código.

ParteEjemploPara qué sirve
Dirección basehttp://localhost:3000/apiIdentifica la API en este ejemplo local.
Recurso/productosLos datos que se consultan o se modifican.
MétodoGET o POSTLeer o crear.
Cuerpo de entradanombre, precio, stockLos datos que viajan en JSON al crear.
RespuestaEstado HTTP y cuerpo JSONLe comunica el resultado al frontend.

La dirección base y la ruta se suman: http://localhost:3000/api más /productos da http://localhost:3000/api/productos. Esa dirección tiene que ser accesible desde el navegador que ejecuta React, y localhost es el computador de ese navegador.

4 Axios: una instancia y un service

La configuración de Axios vive en un solo módulo. Así los componentes no escriben direcciones ni repiten opciones.

src/services/api.js
import axios from 'axios'

// Una instancia comparte dirección base y tiempo máximo entre solicitudes.
export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL || 'http://localhost:3000/api',
  timeout: 10000
})

baseURL es la dirección común: api.get('/productos') la agrega por delante. timeout limita la espera a 10 segundos. Vite lee VITE_API_URL del archivo .env cuando inicia o construye el proyecto.

El service reúne las llamadas HTTP:

src/services/productoService.js
import { api } from './api'

export async function listarProductos(signal) {
  const respuesta = await api.get('/productos', { signal: signal })
  // data es el cuerpo JSON; status y headers pertenecen a la respuesta HTTP.
  return respuesta.data
}

export async function guardarProducto(dto) {
  const respuesta = await api.post('/productos', dto)
  return respuesta.data
}

respuesta.data es el cuerpo JSON y respuesta.status es el estado (200, 201...). En un POST, el segundo argumento es el objeto que Axios envía como JSON. signal permite cancelar la lectura con AbortController cuando la página se desmonta.

AcciónMétodo en AxiosEn el ejemplo
Listarapi.get('/productos')Carga de la pantalla.
Crearapi.post('/productos', dto)Formulario de nuevo producto.
Actualizarapi.put('/productos/ID', dto)Existe en la API; pruébalo en Postman.
Eliminarapi.delete('/productos/ID')Existe en la API y responde 204 sin cuerpo. Es el ejercicio del final.
CORS. React (puerto 5173) y el backend (puerto 3000) son orígenes distintos. El backend deja leer sus respuestas solo al origen exacto que indica CORS_ORIGINS, tanto en Express como en Spring Boot. CORS regula lo que el navegador permite leer y no autentica a nadie.
5 Guardar un producto, paso a paso

El diagrama sigue un clic en Guardar producto, desde el formulario hasta los datos guardados y de vuelta:

Cada flecha corresponde a una pieza del código. Léelas en este orden con el proyecto abierto:

  1. Formulario. Al enviar, enviar en FormularioProducto.jsx cancela la recarga de la página y revisa que el nombre tenga al menos dos caracteres.
  2. DTO del frontend. crearProductoRequestDto convierte los textos del formulario en números y arma el dto. Luego el formulario llama a props.onGuardar(dto).
  3. Página. onGuardar es la función crearProducto de ProductosPage.jsx. Marca que está guardando y llama a guardarProducto(dto).
  4. Service y Axios. guardarProducto ejecuta api.post('/productos', dto). Axios agrega la dirección base y envía el JSON.
  5. Backend: DTO de entrada. La API valida el cuerpo y se queda solo con nombre, precio y stock. Si algo no cumple, responde 400 y el recorrido salta a la sección 7.
  6. Backend: service y datos. El service crea el producto con un id nuevo y lo guarda (en un archivo JSON con Express, en la base H2 con Spring Boot).
  7. Respuesta. La API responde 201 con el DTO de salida: el producto con su id y sin fechaCreacion.
  8. De vuelta en React. Axios entrega el cuerpo en respuesta.data, y guardarProducto se lo devuelve a la página.
  9. Estado. crearProducto agrega el producto a la lista con setProductos y devuelve true. El formulario ve ese true, limpia sus campos y React dibuja la tarjeta nueva.

El DTO: los datos que viajan

DTO significa Data Transfer Object: un objeto con los campos que se transfieren entre dos partes del sistema. No es un componente ni una tabla de la base de datos. En el recorrido hay dos tipos.

En React, el DTO de entrada convierte los textos del formulario en el cuerpo que exige la API:

src/dto/producto.dto.js (frontend)
// Los inputs HTML entregan texto. El contrato de la API exige números.
export function crearProductoRequestDto(formulario) {
  return {
    nombre: formulario.nombre.trim(),
    precio: Number(formulario.precio),
    stock: Number(formulario.stock)
  }
}

En el backend, el DTO de entrada valida y deja pasar solo los campos permitidos, y el DTO de salida decide qué devuelve. Las reglas son las mismas en Express y en Spring Boot:

CampoRegla del DTO de entrada
nombreTexto de 2 a 80 caracteres, sin contar los espacios de los lados.
precioNúmero entre 0 y 100000000.
stockEntero entre 0 y 1000000.
idNo lo envía el cliente, lo genera el servidor. Si llega, se descarta.

El DTO de salida devuelve id, nombre, precio y stock. El campo fechaCreacion queda guardado pero no viaja. El backend valida otra vez aunque React ya lo haya hecho, porque cualquier cliente puede llamar a la API sin pasar por tu formulario.

Este es el mismo POST en cada backend. Primero Express:

Express: src/routes/producto.routes.js
  router.post('/', (req, res) => {
    const entrada = crearProductoEntradaDto(req.body);
    const creado = service.crear(entrada);
    res.status(201).location('/api/productos/' + creado.id).json(crearProductoSalidaDto(creado));
  });

req.body trae el JSON que envió Axios, que express.json() ya interpretó. Si el DTO lo acepta, el service crea el producto y la ruta responde 201 con el DTO de salida.

Y ahora Spring Boot:

Spring Boot: controller/ProductoController.java
    // @Valid ejecuta las validaciones del DTO de entrada antes de llegar al service.
    @PostMapping
    public ResponseEntity<ProductoSalidaDTO> crear(@Valid @RequestBody ProductoEntradaDTO entrada) {
        ProductoSalidaDTO creado = service.crear(entrada);
        return ResponseEntity.created(URI.create("/api/productos/" + creado.getId())).body(creado);

@RequestBody convierte el JSON en un ProductoEntradaDTO y @Valid ejecuta sus validaciones. Si fallan, el manejador de errores responde 400 con la misma forma { mensaje, detalles } que usa Express. Si pasan, el service crea el producto y el controlador responde 201.

Spring Boot: dto/ProductoEntradaDTO.java
// DTO de entrada: lo que el cliente envía en POST y PUT. Solo declara tres campos:
// si llega un id o cualquier otro dato, Jackson lo ignora. El id lo genera el servidor.
@Data
@NoArgsConstructor
public class ProductoEntradaDTO {

    @NotNull(message = "El nombre es obligatorio.")
    @Size(min = 2, max = 80, message = "El nombre debe tener entre 2 y 80 caracteres.")
    private String nombre;

    @NotNull(message = "El precio es obligatorio.")
    @DecimalMin(value = "0", message = "El precio debe ser un número entre 0 y 100000000.")
    @DecimalMax(value = "100000000", message = "El precio debe ser un número entre 0 y 100000000.")
    private BigDecimal precio;

    @NotNull(message = "El stock es obligatorio.")
    @Min(value = 0, message = "El stock debe ser un entero entre 0 y 1000000.")
    @Max(value = 1000000, message = "El stock debe ser un entero entre 0 y 1000000.")
    private Integer stock;

    // Los espacios a los lados no cuentan: se quitan antes de validar el largo.
    public void setNombre(String nombre) {
        this.nombre = nombre == null ? null : nombre.strip();
    }
}

La diferencia está en cómo se escriben las reglas. Express las revisa con una función sobre el cuerpo, y Spring Boot las declara con anotaciones sobre cada campo. En los dos casos, Axios recibe el DTO de salida en respuesta.data.

El frontend organiza sus componentes por niveles. Cada uno tiene un trabajo y solo conoce al nivel de abajo:

De la respuesta al estado

Cuando la página aparece, pide la lista y guarda el arreglo en su estado con setProductos(datos). React dibuja de nuevo, y la página entrega ese estado hacia abajo como props:

src/pages/ProductosPage.jsx
<ListaProductos productos={productos} cargando={cargando} error={errorLista} />

El acceso con punto, props.algo, lee los valores y las funciones que recibe un componente. algo es el nombre de la propiedad: props.productos, props.onGuardar. Así lo hace la lista:

src/components/organisms/ListaProductos/ListaProductos.jsx
import { Row, Col } from 'react-bootstrap'
import { TarjetaProducto } from '../../molecules/TarjetaProducto/TarjetaProducto'

// Organismo: la lista de productos. Según lo que reciba por props, dibuja
// el estado de carga, el error, la lista vacía o las tarjetas.
export function ListaProductos(props) {
  if (props.cargando) return <p role="status">Cargando productos...</p>
  if (props.error) return <p>La lista no está disponible. Usa el botón para reintentar.</p>
  if (props.productos.length === 0) return <p className="text-body-secondary">Todavía no hay productos. Guarda el primero.</p>

  return (
    // xs={12} md={6}: una tarjeta por fila en celular y dos desde tablet.
    <Row className="g-3">
      {props.productos.map((producto) => (
        // key identifica cada tarjeta con el id que asignó el backend.
        <Col xs={12} md={6} key={producto.id}>
          <TarjetaProducto producto={producto} />
        </Col>
      ))}
    </Row>
  )
}

map() convierte cada producto en un elemento y key lo identifica con el id que asignó el backend. La tarjeta lee props.producto.nombre, props.producto.precio y props.producto.stock.

En el formulario, props.onGuardar(dto) llama a la función que le entregó la página. La página hace el POST y agrega a su estado el producto que devolvió el servidor:

src/pages/ProductosPage.jsx: crearProducto
  async function crearProducto(dto) {
    setGuardando(true)
    setErrorGuardado('')
    setExito('')
    try {
      const creado = await guardarProducto(dto)
      // Usamos el DTO de respuesta: su id lo asignó el backend.
      setProductos((anteriores) => anteriores.concat(creado))
      setExito('Producto guardado correctamente.')
      return true
    } catch (error) {
      setErrorGuardado(obtenerMensajeError(error))
      return false
    } finally {
      setGuardando(false)
    }
  }

El formulario limpia sus campos solo si props.onGuardar devuelve true. El bloque finally apaga el estado "guardando" tanto si hubo éxito como si hubo error.

const [nombre, setNombre] = useState('') desestructura el resultado de un hook. No desestructura las props.
7 Cuando algo falla

Axios rechaza la promesa si el estado HTTP queda fuera de 200 a 299, o si nunca llega una respuesta. El catch tiene que distinguir los casos para mostrar un mensaje útil. Este es el camino que sigue el código:

src/services/productoService.js: obtenerMensajeError
export function obtenerMensajeError(error) {
  if (error.response) {
    // Hubo respuesta HTTP: por ejemplo, 400 con errores del DTO de entrada.
    const datos = error.response.data
    if (datos && typeof datos.mensaje === 'string') {
      const detalles = Array.isArray(datos.detalles) ? datos.detalles.join(' ') : ''
      return datos.mensaje + (detalles ? ' ' + detalles : '')
    }
    return 'La API respondió con un error (' + error.response.status + ').'
  }
  if (error.code === 'ECONNABORTED') return 'La API tardó demasiado. Revisa su estado antes de volver a guardar.'
  // El navegador no permite distinguir aquí entre CORS, red y servidor detenido.
  return 'No fue posible contactar la API. Revisa la conexión, su dirección y CORS.'
}

El mensaje aparece dentro de la página, sin alert(). Si falla el guardado, el formulario conserva lo que escribiste. Un timeout no asegura que el servidor no haya guardado, así que actualiza la lista antes de volver a enviar para no duplicar el producto.

8 Míralo en el navegador

Con el ejemplo funcionando, abre las herramientas del navegador (F12) y relaciona cada acción con una solicitud HTTP. Sigue estos pasos en orden:

  1. Abre la pestaña Network y filtra por Fetch/XHR. Recarga la página y busca el GET a /api/productos. Debe tener estado 200.
  2. En Response verás el arreglo que recibe la página. Es el mismo que llega a setProductos(datos) y después a props.productos.
  3. Guarda Cuaderno, precio 2500, stock 8. Ubica el POST y abre Payload: precio y stock viajan como números y no se envía ningún id.
  4. Mira la respuesta 201. El producto vuelve con su id, y eso es lo que crearProducto agrega a la lista.
  5. Presiona Actualizar lista y compara. El GET devuelve un arreglo y el POST devolvió un objeto.
  6. Desde Postman envía un precio negativo y mira el 400 con los detalles del DTO. Piensa qué mostraría React en su catch y por qué el formulario conserva los datos.

Si en desarrollo ves una primera lectura cancelada, es el modo estricto de React comprobando la limpieza del efecto. No significa que el formulario se haya enviado dos veces.

9 Cierre y ejercicio

Antes de seguir, explica con tus palabras el recorrido completo, desde props.onGuardar(dto) hasta el DTO que responde el backend. Señala dónde se valida, dónde se guarda y dónde cambia el estado de React.

Ejercicio: eliminar un producto

La API ya tiene un DELETE. Tu trabajo es agregar al frontend un botón para eliminar. Avanza por etapas y prueba cada una antes de pasar a la siguiente:

  1. En productoService.js, escribe una función eliminarProducto(id) que use api.delete. Recuerda que la respuesta 204 no trae cuerpo.
  2. En ProductosPage.jsx, escribe una función eliminar(id) con try/catch. Si el DELETE funciona, quita ese producto del estado con filter. Si falla, muestra el error con MensajeEstado.
  3. Entrega esa función hacia abajo como una prop con prefijo on, por ejemplo onEliminar, pasando por ListaProductos hasta TarjetaProducto.
  4. En TarjetaProducto, agrega un Boton que llame a props.onEliminar con el id del producto.
  5. Compruébalo en Network: debe aparecer un DELETE con estado 204 y la tarjeta tiene que desaparecer sin recargar la página.

Cuida tres reglas: Axios vive solo en el service, los componentes leen todo con props.algo y la lista se actualiza únicamente después de una respuesta exitosa.
